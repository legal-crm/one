# 29. 세 사이트 연동 점검표 (2026-10-29)

- **사용자 요청:** "모든 기능과 시스템은 변호사 어드민 그리고 통합어드민과 잘 연동되어 있고 문제없이 구현 중인 거야?" → 점검표를 기획서로 만들기.
- **이 문서의 역할:** 00~28 기획서에서 확인한 연동 사실을 한 장에 모은 **원본 지도**예요. 기능마다 원본 데이터(어느 서버 표), 쓰는 쪽, 읽는 쪽, 지금 상태, 고칠 트랙, 연동 시험 번호를 적어요. 착수 후에는 이 표를 연동 시험(4단계 QA)의 기준으로 써요.
- **출처:** 각 줄의 상세 근거는 오른쪽 '트랙'의 기획서에 있어요(코드 위치·줄 번호 포함). 이 문서는 새 코드 조사 없이 기존 점검 결과를 모은 것이에요. 착수 때 줄마다 다시 확인해요.
- **현재 구현 상태:** 기획서의 개선 사항은 **아직 하나도 구현하지 않았어요**(사용자 방침: 기획서를 모두 갱신한 뒤 착수 지시로 한 번에 작업). 마지막 확인은 10-23 `npx tsc --noEmit` 오류 0건이고, 이건 연동이 맞다는 뜻이 아니에요. 계산 엔진 자동 시험 0건, 세 사이트를 잇는 시험(E2E) 미실시.

**상태 표시:** ✅ 서버로 연결됨 · ⚠ 부분 연결(일부 기기 저장·실패 숨김·규칙 구멍) · ❌ 끊김(다른 쪽에 안 감) · ⬜ 아직 없음(새로 만듦)
**주체:** 고객 = 고객 사이트, 사무소 = 변호사 어드민(변호사·직원), 관리자 = 통합어드민

  3. **쓰는 곳은 있는데 읽는 곳이 없음:** 관리자가 고친 값(광고 등급·기준표·쿨다운·콘텐츠)을 고객·사무소 화면이 읽지 않아요.

## 12. 연동 원칙 (모든 새 작업에 적용)

1. **원본 하나:** 기능마다 서버 표 하나가 원본이에요. 다른 화면은 그 표(또는 공개 뷰·서버 함수)를 읽어요. 사본(세션·`localStorage`)은 화면 캐시로만 써요.
2. **세 주체 규칙(RLS):** 고객 본인 / 담당 사무소(`office_id` + 권한) / 관리자는 운영 정보만(제로날리지: 사건 서류·상담 원문 제외). 새 표마다 세 주체 규칙을 적고 시험해요.
3. **쓰기 = 서버 함수:** 금액·상태·한도처럼 규칙이 있는 값은 서버 함수가 계산·검증해요(`create_ad_order`, `create_case`, `record_case_milestone`, `create_fee_agreement_from_contract`, LD-1 한도 등). 화면 직접 insert는 막아요.
4. **실패는 보여 줘요:** 서버 저장 실패를 브라우저 저장으로 대신하지 않아요. 오류 카드·다시 시도.
5. **변경은 전달돼요:** 다른 쪽 화면이 바뀌어야 하는 변경은 실시간 구독 또는 알림(서버 `in_app_notifications`)으로 알려요. 관리자 설정은 버전(게시) 단위로 반영돼요.
6. **기록은 남겨요:** 관리자 조치(`admin_actions`), 사무소 활동(`office_audit_logs`), 사건 기록(`case_events`), 금액 기록(추가만, 취소 사유).
7. **시험 데이터는 운영에 없어요:** DEV 시드·시험 사건은 운영 빌드에서 0건.
