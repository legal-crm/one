## 0. 한눈에 보는 결론 (10-29 CM-Q1~Q8 결정으로 개편 방향 확정)

**지금 사건 관리는 '단계별 작업 화면 6개를 한 장에 모아 둔 것'이고, 단계와 단계 사이가 이어져 있지 않아요.**

1. **'사건'의 실체가 없어요.** 사건 = 상담 요청 번호이고, 사람(의뢰인)과 사건을 나누는 단위가 없어요. 같은 사람이 다시 요청하면 별개 사건이 되고, 계약·채팅·서류는 번호·전화번호·브라우저 저장소를 뒤져서 짝을 맞춰요.
2. **단계 기준이 네 벌이고 서로 어긋나요.** 사건 상태 8개, 13단계, 화면 6단계, 잠금 규칙이 따로 있어요. 화면 단계는 저장되지 않아서 '다음 단계로'를 눌러도 다시 열면 원래 자리이고, 상태→단계 계산이 한 칸씩 늦어요(계약 체결 = 아직 2단계, 접수 = 아직 4단계, 개시결정 = 아직 5단계). '서류 준비'(document)·'변제 중'(repaying) 상태는 어느 화면도 저장하지 않아요.
3. **단계가 바뀌어도 아무 일도 일어나지 않아요.** 계약해도 서류 목록이 안 생기고, 접수해도 기일·할 일·의뢰인 안내가 안 생기고, 개시결정을 넣어도 변제 일정이 안 생겨요. 상태 변경 알림톡은 쓰지 않는 칸반 끌기에서만 나가고, 각 단계 화면의 "알림톡/문자 발송" 버튼은 실제로는 변호사 브라우저에 메모만 남겨요(의뢰인에게 안 감). 4단계 '의뢰인 제출 동의 요청'은 0.6초 기다렸다가 "발송했습니다"를 띄우는 가짜예요.
4. **앞 단계에서 만든 값을 다음 단계가 안 받아요.** 제안서 수임료 → 계약(기본값 30만·100만·50만으로 다시 입력), 계약 → 서류 목록, 사건번호 → 법원 진행 조회(기능은 있는데 화면에 안 붙음), 인가결정일 → 변제 상태. 6단계 연체 횟수는 저장되지 않는 숫자 칸이에요.
5. **목록이 남의 사건까지 보여 줘요.** 화면 목록은 걸러지지 않은 전체 요청을 받아서 다른 변호사의 공개 요청, 휴지통에 넣은 사건, 운영에 섞인 시험 사건 9건을 다 보여 주고, '내 사건만' 권한도 적용되지 않아요. 휴지통 버튼은 아무것도 안 열어요.
6. **저장 구조가 위험해요.** 사건 하나가 jsonb 문서 한 덩어리이고, 처음 한 번만 읽고 새로 읽지 않으며, 저장은 통째 덮어쓰기(마지막 저장이 이김)예요. 다른 직원이 고친 내용은 탭을 다시 열기 전까지 안 보이고, 지운 메모가 되살아나요. 의뢰인 화면은 서버가 아니라 기기 사본을 읽어 사무소가 저장한 게 의뢰인에게 안 닿아요.
7. **끝맺음이 없어요.** 종결 상태가 '취소' 하나라서 상담 이탈·계약 해지·취하·기각·폐지·면책을 구분 못 하고, 기각 처리 때 '상담 이탈 사유' 창이 떠요. 면책일·기각일은 결정일이 아니라 '오늘'로 들어가고, 다시 열기·보관함·5년 보관 뒤 파기가 없어요.
8. **경쟁사는 '사건 하나 = 한 화면 + 고정 사건 카드 + 순서대로 놓인 업무'예요.** 리걸프렌즈는 모든 하위 화면 왼쪽에 사건 카드(사건번호·담당자·진행현황·기각/폐지/종료 여부)를 고정하고, 업무 아이콘 9개를 진행 순서대로 두며, 진행현황이 작업에 따라 바뀌어요('상담대기' → '서류준비'). 수임료 화면은 "계약서 수임료 내역 가져오기"로 계약을 원본으로 써요. 사건번호를 등록하면 진행 상황이 자동 갱신되고 의뢰인 앱에 집회기일·납입일 알림이 가요. 해외 Clio는 단계(칸반)마다 할 일 목록을 자동으로 붙이고, 의뢰인에게 보여 줄 단계 이름을 따로 둬요.

**개편 방향 — 등뼈 하나:**
- **의뢰인(사람)과 사건을 나눠요.** 한 사람이 여러 사건(재신청·파산 전환)을 가질 수 있어요.
- **사건 상태는 서버 한 곳, 세부 단계 하나.** 회생·파산 각각의 세부 단계표 → 화면 6묶음 → 의뢰인용 단계 이름이 같은 표에서 나와요.
- **상태는 '기록'이 움직여요.** 계약 체결 기록, 사건번호 등록, 개시결정 입력, 인가결정 입력, 면책결정 입력이 각각 다음 상태를 만들고, 그때마다 **정해진 후속 일(할 일·기일·의뢰인 안내·다음 단계 준비물)이 자동으로 생겨요.** 사람이 상태를 직접 바꾸는 건 사유와 함께 예외로만.
- **사건 화면은 고정 사건 카드 + '지금 할 일' + 단계 작업 + 통합 타임라인.**
- **목록은 내 범위만, 다음 기일·기한 중심.**
- **법원 사건 조회(이미 있는 CODEF 경로)를 사건번호에 붙여** 진행 변화를 '확인 필요'로 알려요(자동 반영은 안 함).
- **끝까지:** 변제 수행 장부 → 면책 → 종결 사유·결정일 → 보관함 → 5년 뒤 파기, 필요하면 다시 열기.

### 1-3. 의뢰인 쪽

- 마이페이지·'내 사건' 진행 카드는 **기기 사본**(`getCrmClientSync`)을 읽어요 → 사무소 저장이 안 닿아요(S·H-14와 같은 원인: 사건 기록 보안 규칙 키 = 상담 요청 번호).
- 진행 카드 문구는 13단계 값을 기준으로 나오는데, 단계 화면들이 집회·인가·금지명령·보정기간 단계를 저장하지 않아 그 안내가 나오지 않아요.
- 사무소가 보내는 "앱 알림"(`addClientNotification`)은 변호사 브라우저에 쌓여요.
- 의뢰인 '변호사에게 면책신청 요청하기'는 인가 전에도 보이고, 사무소 화면에 나타나지 않아요.

## 2. 흐름이 끊기는 곳 (심각한 순)

## 4. 개편 설계

### 4-1. 의뢰인과 사건 나누기 (CM-1)

| 테이블 | 내용 |
|:---|:---|
| `office_clients` | 사무소의 의뢰인(사람): 사무소, 실명·연락처(공개 동의 뒤), 스텔스 가명, 마이김변 회원 연결(있으면), 전화번호 지문(중복 확인용), 메모, 만든 경로 |
| `cases` | 사건: 사무소, 의뢰인, 사건 유형(회생/파산), **세부 단계**(4-2), 화면 묶음(계산값), 담당 변호사·담당 직원, 출처(마이김변 상담 요청 id / 영업 DB 리드 id / 직접 등록 / 가져오기), 사건번호·법원(대표값), 종결 사유·결정일, 보관 시작일·파기 예정일, **버전 번호** |
| `case_events` | 사건 타임라인(추가만): 종류(단계 변경·기록·소통·서류·수납·법원 감지·메모), 내용 요약, 연결 id, 누가·언제, 의뢰인 공개 여부 |

- **사건이 생기는 길 하나:** 마이김변 상담 요청 → (의뢰인이 '상담 시작'·연락처 공개) → 사건 생성 / 영업 DB 이관(SL-9) / 직접 등록 / 엑셀 가져오기 → 모두 `create_case`(서버 함수) 하나. 같은 사무소에 같은 전화번호 지문의 의뢰인이 있으면 "같은 분인가요?"를 묻고 묶어요(자동 합치기 없음).
- **기존 데이터:** 지금 `crm_clients`(상담 요청 번호 = 사건)를 사건 1건씩으로 옮기고, 같은 사람은 사람이 확인해 묶어요. 서식 작성 데이터(진술서·재산·수지 등)는 당분간 지금 칸(jsonb)에 두되 `cases.id`로 연결하고 **부분 저장**(바뀐 칸만, 버전 확인)으로 바꿔요(4-10). 수임료(FE-2)·보정(CR-1)·서류(DP-6)·소통(CL-1)·검토(CV-1)는 각 트랙의 새 테이블로.
- **권한:** 사무소 기준(RB-1 `has_office_permission`), 의뢰인은 자기 사건의 공개 항목만, 통합관리자 제외.

### 4-2. 단계표 하나 (CM-2)

세부 단계 하나가 상태·화면 묶음·의뢰인 문구를 모두 정해요. 지금의 8개 상태·13단계·6단계·잠금 규칙은 이 표에서 계산해요.

**개인회생**

| 세부 단계 | 화면 묶음 | 들어오는 기록 | 의뢰인에게 보이는 이름 |
|:---|:---:|:---|:---|
| 상담 | 1 | 사건 생성 | 상담 중 |
| 제안서 발송 | 1 | 제안서 발송 | 제안서를 받았어요 |
| 계약 진행 | 2 | 계약서 발송 | 계약서 서명 대기 |
| 수임 | 2→3 | 계약 체결(전자·종이·우편) | 사건 준비 시작 |
| 서류 준비 | 3 | (수임과 동시) | 서류를 모으고 있어요 |
| 신청서 작성 | 4 | 필수 서류 받음 비율 기준 또는 변호사 '작성 시작' | 신청서를 쓰고 있어요 |
| 접수 | 4→5 | 사건번호 등록 | 법원에 접수했어요 |
| 보정 | 5 | 보정 회차 등록(CR) | 법원 보완 요청 대응 중 |
| 개시결정 | 5→6 | 개시결정일 입력 | 개시결정이 났어요 |
| 채권자집회·이의기간 | 6 | 집회일·이의기간 입력 | 채권자집회를 앞두고 있어요 |
| 인가·변제 | 6 | 인가결정일 입력 | 변제를 하고 있어요 |
| 면책 | 6 | 면책 신청·결정일 입력 | 면책 결정 |
| 종결 | - | 종결 기록(4-9) | 사건이 끝났어요 |

**개인파산** (BK-5와 같은 표): 상담 → 제안서 → 계약 → 수임 → 서류 준비 → 신청서 작성 → 접수(하단·하면 번호) → 보정·예납 → 파산선고(동시폐지/관재) → 관재인 면담·자료 제출 → 채권자집회·의견청취 → 면책 이의기간·면책심문 → 면책 결정·확정 → 종결.

- 화면 묶음 6개 이름은 그대로 두되 파산은 5 '보정·파산선고', 6 '면책'.
- **화면 단계는 저장된 세부 단계에서 계산**(한 칸 늦는 문제 없음). 앞 묶음을 다시 보는 건 자유, 앞으로 가는 건 기록으로만.
- 의뢰인 문구는 사무소가 고칠 수 있고, 판단·가능성 표현은 넣지 않아요(제109조, 금지 표현 검사).

### 4-3. 기록이 상태를 움직이고, 후속 일이 자동으로 생겨요 (CM-3)

서버 함수 `record_case_milestone(사건, 종류, 값)`이 ① 잠금 규칙 확인 ② 세부 단계 변경 ③ 타임라인 ④ 후속 일 생성을 한 번에 해요. 버튼·화면 어디서 누르든 같은 함수예요.

| 기록 | 다음 세부 단계 | 자동으로 생기는 일 |
|:---|:---|:---|
| 제안서 발송 | 제안서 발송 | 응답 기한 할 일(LD-Q2 2영업일), 의뢰인 알림 |
| 계약 체결 | 수임 → 서류 준비 | **수임료 약정·회차 생성(FE-3)**, **사건 사실 기준 서류 목록 생성(DP-1)**, 의뢰인 '서류 준비' 안내 + 1차 서류 요청(H-14), 담당 직원 할 일 '서류 요청 확인', 위임장·경유확인서 준비 |
| 필수 서류 받음 ≥ 사무소 기준 | 신청서 작성 | 작성기 자료 채움 확인(H-10), 변제계획 초안(B-3), 할 일 '신청서 검토' |
| 사건번호 등록(+ 접수일·법원) | 접수 | **법원 사건 조회 연결(CM-7)**, 금지명령 결과 확인 할 일(3~5일 뒤), 회생위원 면담 대비 안내, 의뢰인 '접수 완료'(알림톡 C-5 ATS_06), 접수 서류 사본 보관 |
| 보정 회차 등록 | 보정 | CR-2(법원 기한·사무소 마감·일정·의뢰인 '보정 할 일') |
| 금지·중지명령 결과 | (그대로) | 결과 기록, 의뢰인 안내 |
| 개시결정일 입력 | 개시결정 | **변제 회차 장부 생성(CM-8)**, 가상계좌 안내, 제1회 변제일이 지났으면 '한 번에 낼 금액' 안내, 이의기간 만료일 일정, 채권자 이의 확인 할 일(기존 템플릿) |
| 집회일 입력 | 채권자집회 | 일정, D-7·D-1 출석 안내(신분증·본인 출석), 고지사항 카드 |
| 인가결정일 입력 | 인가·변제 | 상태 '변제 중'(지금은 안 바뀜), 인가 뒤 변제 안내, 조건부 인가면 매년 소득 보고 할 일 |
| 변제 마지막 회차 | 면책 | 면책신청서 준비(H-0 작성기), 의뢰인 '면책 신청 준비' |
| 면책 결정일 입력 | 면책 | 확정일 일정, 압류 해제 신청 안내(파산), 종결 준비 |
| 종결 기록 | 종결 | 4-9 |

- **알림 발송은 KT-2 설정**(알림톡/담당자 카톡/둘 다/안 보냄)을 따르고, 템플릿 심사(C-5)가 끝난 것만 실제로 나가요. 화면은 "보냈어요/못 보냈어요(사유)"를 사실대로 보여 줘요. 브라우저 메모로 대신하지 않아요.
- **단계 할 일 템플릿(CM-4):** 지금 있는 `taskTemplateService` 내용을 세부 단계마다 붙이고 사무소가 고쳐 써요(역할별 배정, 기한 = 기록일 + n일). 할 일은 업무함(HM-3)에 모여요.
- **사람이 상태를 바꿀 때:** 대표·담당 변호사만, 사유 필수, 타임라인에 '수동 변경'으로. 칸반 끌기·목록 바로 바꾸기도 같은 함수.

### 4-4. 화면이 '지금 할 일'을 먼저 보여 줘요 (CM-5)

```
┌ 고정 사건 카드 (모든 묶음에서 그대로) ─────────────────────────────┐
│ 의뢰인(가명/실명) · 사건 유형 · 사건번호·법원 · 담당 변호사/직원        │
│ 세부 단계 · 다음 기일(D-n) · 서류 n/m · 수임료 남은 금액 · 종결 여부     │
│ [채팅] [전화(업무폰)] [카톡] [일정 등록] [정보 수정]                    │
└──────────────────────────────────────────────────────────────┘
[레일] 1 상담 ─ 2 계약 ─ 3 서류 ─ 4 접수 ─ 5 보정·개시 ─ 6 변제·면책   (지금 묶음 강조, 지난 묶음 다시 보기)
┌ 지금 할 일 (이 사건의 업무함) ─────────────┐ ┌ 오른쪽 패널(CL-5) ────────┐
│ ● 기한 지남 / 오늘 / 이번 주 / 의뢰인 회신 대기 │ │ 소통 기록 · 녹음 · 메모 · 할 일 │
│ 버튼 하나로 그 작업 화면 열기                 │ └──────────────────────┘
└─────────────────────────────────────┘
[묶음 작업 화면] (지금 Stage1~6 화면을 다듬어 사용)
[타임라인] 단계·기록·소통·서류·수납·법원 감지 한 줄 (필터)
```

- 주 버튼은 '다음 단계로' 대신 **그 단계의 기록 버튼**('계약 체결 기록', '사건번호 등록', '개시결정 입력'…)이에요.
- 완료 조건 체크리스트는 대리 조건을 빼고 실제 기록으로만(예: '금지명령 결과 기록됨').
- 단계 묶음 안 세부 탭과 바로가기 번호를 하나로 정리(알림·업무함에서 정확한 탭으로).
- 묶음 화면은 각 트랙이 맡아요: 1 = CV 사건 검토·제안서(B-5), 2 = 계약 위저드·FE, 3 = DP, 4 = H·BK, 5 = CR·BK-5, 6 = CM-8·BK-5·H-0.

### 4-5. 목록 (CM-6)

- **범위:** 내 사무소·내 권한 범위만(RB-4: 대표·변호사 전체, 직원은 배정 사건), 휴지통·종결 보관함 분리, 시험 사건 제외(HM-1).
- **열:** 의뢰인 · 사건 유형·사건번호·법원 · 세부 단계 · **다음 기일/기한(D-n)** · 다음 할 일(실제 업무함 첫 항목) · 담당 · 수임료(남은 금액·연체) · 최근 활동.
- **보기:** 전체 / 묶음별 / 기한 지남 / 이번 주 기일 / 의뢰인 회신 대기 / 미배정 / 종결 보관함 / 휴지통. 저장된 보기는 서버(사람별).
- **바로 바꾸기:** 단계(잠금 규칙·사유 확인), 담당 배정, 메모 한 줄. 일괄: 배정·안내 보내기·내보내기(권한·기록).
- **같은 사람 여러 사건:** 의뢰인 이름 아래 '사건 2건' 표시, 의뢰인 화면에서 사건 이력.
- **칸반:** 세부 단계 기준, 끌면 4-3 함수(사유 창).
- **캘린더:** 일정 서버 데이터(HM-5·T-5)를 그대로.

### 4-6. 등록·이관 (CM-1과 함께)

- 직접 등록 = 이름·휴대폰·사건 유형·(선택) 접수 예정일·유입 경로만. 나머지는 사건 화면에서. 지어낸 기본값(나이 0, '직장인', 'LIVING' 등) 금지.
- 등록하면 의뢰인 초대(알림톡 링크 → 로그인 → 내 사건 연결, H-14 방식)를 고를 수 있어요(디던비 '사건방').
- 영업 DB 이관(SL-9), 마이김변 상담 요청 → 사건(의뢰인 동의 뒤), 엑셀 가져오기 모두 같은 함수·같은 중복 확인.

### 4-7. 법원 사건 조회 연결 (CM-7)

- 사건번호를 등록하면 **이미 있는 CODEF '대법원 나의사건검색' 경로**로 조회해 사건 카드에 재판부·회생위원·최근 진행 내역을 보여 줘요.
- **하루 1회 감지(G-1 스케줄러):** 진행 내역에 새 줄(보정명령·개시결정·집회기일 지정·인가·면책 등)이 생기면 사건 타임라인에 '법원 진행 감지 — 확인 필요'와 업무함 항목을 만들어요. 사람이 '기록으로 반영'을 눌러야 4-3이 돌아요(자동 반영 없음, CR-11과 같은 원칙).
- 동기화는 **바뀐 칸만 붙이고**, 사무소가 넣은 개시결정일·가상계좌 등을 지우지 않아요(지금 `CourtCaseTab` 통째 교체 버그).
- 결과는 서버(사건 단위)에 저장, 브라우저 캐시만 쓰지 않아요. CODEF 계약·요금(조회 건당)은 A-5 비용에 넣고, 키가 없으면 '수동 조회 바로가기'(대법원 사이트 링크 + 사건번호 복사)만.

### 4-8. 변제 수행 관리 (CM-8)

- **법원 변제금 회차 장부** `case_plan_payments`: 개시결정·변제계획 기준 회차·예정일·금액·납부 확인(사무소 기록 / 의뢰인 '납부했어요' / 법원 조회 대조), 미납 회차 수.
- 회생동행의 납부 기록(의뢰인)을 서버로 옮겨(S·BK-8) 이 장부와 연결 — 의뢰인이 쓰면 사무소 화면에 보이고, 사무소 확인 전엔 '확인 중'.
- **경고:** 미납 1회 = 의뢰인 안내 제안, 2회 = 담당 변호사 할 일, 3회분 = '폐지 위험' 할 일(관할별 기준 표시는 참고 정보). 문구는 압박 없이 사실과 연락 안내만.
- 인가 전 적립금도 같은 장부(개시결정 ~ 인가 사이 회차).
- 변제계획 변경 신청·면책 신청 준비 버튼은 서식 작성기(H) 해당 서식으로.
- 수임료 수납(FE)과 화면·이름·색을 나눠요('변제금 = 채권자에게 가는 돈').

### 4-9. 종결·보관·다시 열기 (CM-9)

| 종결 사유 | 언제 | 기록 |
|:---|:---|:---|
| 상담 종료(수임 안 함) | 계약 전 | 이탈 사유(지금 창) |
| 계약 해지·사임 | 계약 뒤 | 해지일·사유, 수임료 정산(FE-10) |
| 신청 취하 | 접수 뒤 | 취하일 |
| 기각 / 폐지(이시폐지·변제 불이행 폐지) | 법원 결정 | **결정일**(오늘 아님), 결정 종류, 대응(항고 검토) 할 일 |
| 면책 / 파산종결·면책 확정 | 법원 결정 | 결정일·확정일 |
| 회생 → 파산 전환 | 사무소 판단 | 새 파산 사건 만들고 연결(같은 의뢰인), 자료 이어받기 |

- 종결되면 목록 '종결 보관함'으로, **보관 시작일 = 종결일, 5년 뒤 자동 파기 예정일**(10-24 결정 '종결 5년'), 파기 30일 전 대표 알림, 파기 기록.
- **다시 열기:** 대표·담당 변호사, 사유 필수, 이전 단계로 복귀, 타임라인 기록. 휴지통(잘못 만든 사건)은 30일 복구 그대로 두고 실제로 동작하게.
- 의뢰인 화면: 종결 안내(면책이면 회복 아카데미, 기각·폐지면 사무소 연락 안내만, 판단 문구 없음).

### 4-10. 저장·동시 작업 (CM-10)

- `cases`·각 트랙 테이블은 행 단위 저장. 남는 jsonb(서식 작성 데이터)는 **바뀐 칸만 보내는 저장 함수 + 버전 확인**: 버전이 다르면 "다른 사람이 먼저 고쳤어요 — 새로 불러오기/내 변경 비교"를 보여 줘요. 지운 메모가 되살아나는 로컬 병합은 없애요.
- **새로 읽기:** 사건 화면을 연 동안 Supabase 실시간 구독(사건·타임라인 행), 끊기면 30초 폴링. 목록은 화면 복귀 때 새로 읽기.
- 서버 저장 실패는 언제나 화면에 표시(3단계 포함), 기기 사본으로 조용히 대체하지 않아요(6-1 원칙).

### 4-11. 의뢰인 화면 연결 (CM-11)

- 마이페이지 '내 사건'은 **서버의 `cases` + 공개 이벤트**를 읽어요(사건별, 여러 사건이면 고르기). H-14의 의뢰인 연결 방식(로그인 계정 ↔ 사건 의뢰인)을 같이 써요.
- **절차 그림:** 회생 10칸·파산 칸을 세부 단계표의 의뢰인 문구로 그리고 지금 칸 강조(리걸프렌즈 설명서 절차도·똑생 Step 참고).
- **다음 일정·할 일:** 집회·면담·보정 마감·납입일, 의뢰인 몫 할 일(서류·보정·진술서·면책 서류), 사무소 담당자 연락.
- 앱 알림은 서버 저장(`client_notifications`)으로 바꾸고, 알림톡·카톡(KT-2)과 같은 사건 이벤트에서 생겨요.
- 면책 신청 요청 버튼은 '인가·변제' 단계 이후에만, 누르면 사무소 업무함에 와요.
- 보이지 않는 것: 사무소 내부 메모·검토·판단, 계산값(변호사가 보낸 제안서 제외).

### 4-12. 코드 정리 (CM-12)

- `CrmTab`을 목록·사건 화면·모달 묶음으로 나누고, 사건 화면 상태는 사건 데이터 훅 하나로(지금 상태 120개·렌더 안 500줄).
- 죽은 코드 삭제: 불러만 둔 컴포넌트 약 20개, 화면에 안 붙은 처리 함수 6개, 846줄 옆 패널, 닿지 않는 '신규 리드' 보기, `_backup` 파일. 필요한 부품(법원 조회·폐지 방어 신청서 등)은 새 구조에 옮겨 연결.
- 사건 화면 안 고정 계산(생계비 133/220/282/343, '예상 탕감률')·`localStorage['electronic_contracts']` 읽기 삭제 → 각 트랙 서버 값.
- 시험 사건·시연 프로필 운영 제외(HM-1), 시연 데이터의 잘못된 13단계 id 정리.

## 8. 완료 기준

- 마이김변 상담 요청·영업 DB 이관·직접 등록·엑셀 가져오기가 모두 같은 사건 구조로 들어오고, 같은 번호의 의뢰인은 묶을지 물어요. 한 의뢰인 화면에서 사건 이력(재신청·전환)이 보여요.
- 계약 체결을 기록하면 **그 자리에서** 수임료 회차·사건 맞춤 서류 목록·의뢰인 서류 요청·담당 직원 할 일이 생기고, 사건이 '서류 준비'로 보여요. 다시 열어도 같은 단계예요.
- 사건번호를 등록하면 법원 조회 결과가 사건 카드에 나오고, 금지명령 결과 확인 할 일과 의뢰인 접수 안내(발송 결과 표시)가 생겨요. 법원 진행에 새 줄이 생기면 다음 날 업무함에 '확인 필요'가 떠요.
- 개시결정일을 넣으면 변제 회차 장부·이의기간 일정·가상계좌 안내가 생기고, 인가결정일을 넣으면 '변제 중'이 돼요. 의뢰인이 '납부했어요'를 누르면 사무소 장부에 '확인 중'으로 보여요. 미납 3회분이면 담당 변호사 업무함에 떠요.
- 기각·폐지·면책을 결정일과 함께 기록하면 종결 보관함으로 가고 파기 예정일이 보여요. 다시 열기가 돼요. 휴지통 버튼이 실제로 열려요.
- 사건 목록에 남의 사건·삭제 사건·시험 사건이 0건이고, 직원은 배정 사건만 봐요. 다음 기일 순으로 정렬돼요.
- 두 직원이 같은 사건을 동시에 고치면 뒤에 저장한 쪽에 "먼저 고친 내용이 있어요"가 뜨고, 지운 메모가 되살아나지 않아요. 다른 PC에서 고친 내용이 열려 있는 화면에 반영돼요.
- 의뢰인이 다른 기기에서 로그인해도 내 사건 단계·다음 일정·할 일이 서버 값으로 보여요. 사무소가 보낸 안내가 의뢰인 알림에 남아요.
- 사건 화면·의뢰인 안내에 "개시결정이 인가", 지어낸 변제율·면책률, '8대/4대/7대', 이모지 상태 0건.
